# 均衡粒度的证明任务蓝图

原来的 58 个节点保留为数学里程碑，在这里展开为可独立交付和验收的小任务。原节点编号、论文陈述、现有证明映射和完成状态继续由上一级 `manifest.json` 管理。本目录是其工作分解层。

- [任务总览](OVERVIEW.md)：按工作包和任务编号浏览。
- [详细任务](NODES.md)：精确数学目标、依赖、论文位置、验收条件和原义务覆盖表。
- [机器可读清单](manifest.json)：里程碑、任务、验收门槛及证据对应。
- [完整依赖图](DEPENDENCIES.mmd)：包含原里程碑和细分任务。
- [检查结果](validation.json)：数量、无环依赖、主链闭包和逐条义务覆盖。
- [现有成果逐项验收](AUDIT.md)：完整完成、部分完成、尚未实现的清单，以及冻结源码和实际构建证据。

## 拆分标准

普通证明任务围绕一项明确数学输出组织，通常以新增约 200–600 行 Lean 为初始粒度。复杂局部任务可以暂估到 750 行；超过 800 行，或实现中显现两个可独立处理的困难，就继续拆分。每项至少有两条具体的数学验收条件。组合任务与已有结果复用任务通常更小，清单用 `kind` 区分这三类任务。

这些区间是拆分启发式，未经实际证明校准。已有库的覆盖、闭域识别及分析基础的困难仍可能使某项需要再次展开。因此任务比原来接近等量，但不承诺数学难度相同，也不能把区间简单相加作为剩余代码预测。

已完整完成的 S01、S02、R01 各保留一项，不为凑数量重拆。任务定义继续保存在 `parts/*.json`，逐项核对和完成证据另存在 `audit/progress.json`，生成时覆盖进当前任务状态：

- `retained_proof`：保留的原有完整局部结果，也经过本轮证据复核。
- `complete`：完整目标及全部验收条件已有对应 Lean 声明，冻结源码构建、声明所属模块核验和 owner-based 公理审计均通过。
- `partial`：已有实质支持，但尚有明确缺口。
- `planned`：冻结快照中未见该任务的实际实现。

这是对已有成果的补登记，原来 19 个部分节点的证明不会归零，也不会因几个子任务完成便自动升级整个父里程碑。通用条件定理可以完成一个明确的通用子任务；输入非空、实际几何见证及主定理的存在性仍须对应任务另行完成。

## 依赖和后续实例化

每项列出本地子任务依赖，并保留原父节点的上游里程碑依赖。细化中暴露的额外依赖必须有明确理由，参与完整图的无环检查。例如函数空间 smooth tame 需要实际加权 levels，二模归一化切片需要 R12 构造的真实边框行。

一些原节点的 `remaining_obligations` 同时包含通用理论及后续具体实例化。例如 H01 的通用 tame 理论供 W02 使用，而具体 Sobolev 实例化在 W02 验收；D01 的通用曲率理论供 G15 使用，而实际向外法向在 G15 识别。这类义务在覆盖表中明确委托给实际承担的下游子任务，并附原因。

覆盖定位不自动建立反向证明依赖，避免把“使用某通用定理”与“实例化该通用定理”误连成循环。但原里程碑的全部项目义务，仍须其 `acceptance_tasks` 中的后续实例化一并验收，不能只完成通用部分便宣称整个节点闭合。检查器要求主链的委托目标也在 MAIN 的必要任务闭包内。

几何通用定理仍可按原蓝图提前证明。最终 MAIN 必须用 N12/G01 实际构造的同一 Core、同一发展、同一补帽和同一相位族，不能留下输入非空、逆存在或 Nash–Moser 结论的假设。

## 执行和维护

任务的 `owner_role` 继承原工作包；本目录不分配或扩大文件写入权。真正实施前仍须核对 `coordination/active-workers.json`，公共接口、根导入、公理审计及最终完成声明仍按原分工处理。

编辑 `parts/*.json` 后，在项目根目录运行：

```powershell
python -X utf8 blueprint/refinement/check.py --write
python -X utf8 blueprint/refinement/check.py
python -X utf8 blueprint/refinement/test_check.py
```

检查器逐字保留原目标、验收条件、剩余义务及论文位置，检查子任务唯一编号、完整覆盖、组合步骤、无悬空依赖、无环图、完整 MAIN 闭包、工具链及 mathlib 锁定。它还会拒绝无依据的新增完成状态、未说明的跨父义务委托和超过再次拆分阈值的任务。

完成登记逐项保留完整目标及每条验收条件的证据对应、准确声明名、源文件哈希、构建终态和剩余义务。检查器还要求声明实际所属模块与所引用文件相同，声明检查绑定同一冻结构建及 olean 哈希，拒绝把旧快照的检查结果混入新快照。

机器检查验证证据链的完整性；目标与定理类型的数学语义对应由逐项审阅记录说明。它不自动证明数学目标，也不替代 Lean。子任务真正完成时仍须交付精确 Lean 类型、论文对应、实际所属模块构建终态、新 imports、剩余义务及 owner-based 公理审计结果。

## 逐项验收的验证边界

为逐项验收，将当前 102 个 Lean 源文件及锁定配置冻结到独立目录。使用同一 Lean 4.35.0-rc3、每进程四线程重编，输出只写入隔离目录，依赖包只读取现有缓存，不触发共享依赖构建。构建失败的文件不能为完整完成的任务提供证据。

随后导入全部通过的快照模块，按项目模块所有权检查全部声明及传递公理（包括私有辅助声明），另检查 unsafe；允许公理仅为 propext、Classical.choice、Quot.sound。每个完成项的准确声明还须在这个环境解析成功，并核对实际所属模块。快照、逐模块日志、声明类型和审计结果保存在 `audit/`。

本轮没有修改项目 Lean 源码、工具链、依赖锁、主蓝图或根审计入口。部分新模块尚未纳入总控根入口，本层独立验收不冒充总控的统一构建或完整主定理完成审计。冻结后其它对话继续写入的新成果不混入本次计数；更新计数须核对新源码和证据。
